# GroupGuard — POC (הוכחת היתכנות)

מימוש שלב ה-POC של "GroupGuard", לפי מסמך האפיון `../אפיון_מערכת_סוכן_ניטור_קבוצות_וואטסאפ.md`
(סעיף 3.0). מטרת השלב: לוודא שהרעיון עובד מקצה לקצה על **קבוצת וואטסאפ אחת אמיתית**,
לפני השקעה במוצר SaaS מלא (Multi-Tenant, חיוב, פאנל מלא וכו').

## מה יש כאן

```
poc/
├── .env.example              ← כל החיבוריות (API keys) להזנה — התחילו כאן
├── config/
│   ├── rules.yaml             חוקי הקבוצה (דטרמיניסטיים + סמנטיים), בקובץ ולא בפאנל
│   └── contacts.yaml          אנשי קשר לקבלת התראות
├── connector-whatsapp/        שירות Node.js — המספר הקורא (Baileys, לא-רשמי)
└── app/                       שירות הליבה (Python/FastAPI) — קליטה, AI, חוקים, התראות, דו"ח, פאנל
```

### ארכיטקטורה (תואמת לסעיף 4 + 10.2 במסמך האפיון)

```
WhatsApp group ──► connector-whatsapp (Baileys, Reader) ──HTTP webhook──► app/main.py (FastAPI)
                                                                              │
                                                                              ├─► app/media.py     (Claude Vision — תמונות/סטיקרים)
                                                                              ├─► app/rules_engine.py (דטרמיניסטי + סמנטי / Claude)
                                                                              ├─► app/notifier.py  ──► WhatsApp Business Cloud API (Sender הרשמי)
                                                                              ├─► app/reports.py   ──► SMTP של Gmail (דו"ח יומי)
                                                                              └─► /dashboard        (פאנל HTML לצפייה)
                                                                              (הכל נשמר ב-SQLite: data/groupguard.db)
```

מספר **קורא** (unofficial/Baileys) ומספר **שולח** (Meta Cloud API רשמי) מופרדים
בכוונה — זו ההחלטה הארכיטקטונית המרכזית של הפרויקט (סעיף 10.2), שנועדה לצמצם
את הסיכון לחסימת המספר הקורא: הוא לעולם לא שולח הודעות יזומות.

## התקנה — שלב 1: תלויות

```bash
# שירות הליבה (Python)
cd poc
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt --break-system-packages   # או ללא הדגל אם אתם בתוך venv

# ה-connector (Node.js)
cd connector-whatsapp
npm install
```

## התקנה — שלב 2: חיבוריות ה-API (הקובץ שביקשתם)

```bash
cp .env.example .env
```
ואז מלאו ב-`.env` את הפרטים הבאים:

| מה | איפה משיגים | חובה ל-POC? |
|---|---|---|
| `ANTHROPIC_API_KEY` | [console.anthropic.com](https://console.anthropic.com/) → API Keys | **כן** — בלי זה אין סיווג חוקים סמנטיים ולא הבנת תמונות/סטיקרים |
| `READER_WHATSAPP_NUMBER` | המספר הנייד (E.164) שדרכו יעבוד הסוכן — הזינו *לפני* הרצת ה-connector כדי להתחבר בקוד צימוד במקום QR (ראו `connector-whatsapp/README.md`) | כן |
| `WA_CLOUD_API_TOKEN`, `WA_CLOUD_API_PHONE_NUMBER_ID` | [developers.facebook.com](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started) → יצירת אפליקציית WhatsApp Business | לא חובה מיידית — כל עוד `ALERTS_SEND_VIA_WHATSAPP=false` ההתראות נשלחות במייל בלבד |
| `WA_ALERT_TEMPLATE_NAME` | תבנית הודעה שתאשרו מול Meta (Message Templates) | נדרש לפני ש-`ALERTS_SEND_VIA_WHATSAPP=true` |
| `SMTP_USER` / `SMTP_PASSWORD` | כתובת ה-Gmail שלכם + [App Password](https://myaccount.google.com/apppasswords) בן 16 תווים (דורש אימות דו-שלבי בחשבון) | כן, לדו"ח היומי ולהתראות בזמן אמת |
| `CONNECTOR_SHARED_SECRET` | כל מחרוזת אקראית ארוכה — סוד פנימי בין שני התהליכים | כן |
| `SECRET_KEY` | מחרוזת אקראית וארוכה (נוצרה אוטומטית עבורכם) — חותמת את ה-session cookies של המשתמשים המחוברים | כן — אל תשנו אחרי שיש משתמשים מחוברים |
| `ADMIN_PASSWORD` | סיסמת אדמין יחידה (נוצרה אוטומטית עבורכם) לכניסה ל-`/admin` (פאנל CRM) | כן, לפאנל האדמין בלבד |

**את `MONITORED_GROUP_ID` ואת `DAILY_REPORT_RECIPIENTS` אין למלא ידנית** —
שני אלה מתמלאים אוטומטית לאחר אשף ההרשמה: הקבוצה המנוטרת נקבעת אוטומטית
מהאירוע הראשון שמגיע מהקבוצה שאליה הוספתם בפועל את מספר ה-Reader (ראו
`app/main.py` — `whatsapp_reader_webhook`), ונמען הדו"ח היומי הוא כתובת
המייל של המשתמש שנרשם באשף (ראו `app/reports.py`). כמו כן, ההתראה על כל
הפרה נשלחת **מיידית** בזמן אמת לכתובת המייל של איש הקשר שהוזן באשף ההרשמה
(לא למספר וואטסאפ) — ראו `app/notifier.py`.

ל-Gmail: השליחה היא דרך SMTP (`smtp.gmail.com:587`) עם App Password — אין
OAuth, אין דפדפן, אין קובץ credentials. יש להפעיל אימות דו-שלבי בחשבון
ה-Gmail, ליצור App Password ב-https://myaccount.google.com/apppasswords,
ולהזין אותו כמות שהוא (16 תווים, בלי רווחים) תחת `SMTP_PASSWORD`. סיסמת
החשבון הרגילה לא תעבוד — Google חוסמת שימוש בה מול SMTP חיצוני.

## אשף הרשמה למשתמש קצה (Onboarding) — Multi-tenant

כניסה ל-**http://localhost:8000/** (או ישירות ל-`/onboarding`) פותחת אשף
בן 4 שלבים — פרטי חשבון (שם/אימייל/סיסמה/שם קבוצה), אנשי קשר להתראות (עד 3,
כולל שעות שקט), רמת הקפדה לחוקים (מקל/בינוני/מחמיר) + חוקים בשפה חופשית,
וסיכום. בסיום מוצג **מספר הטלפון** שיש להוסיף לקבוצת הוואטסאפ (F-2.2),
לקוח מ-`READER_WHATSAPP_NUMBER` ב-`.env` — אותו מספר שהזנתם לפני הרצת
ה-connector, כי ב-POC אין הקצאה אוטומטית ממאגר מספרים (זה שלב MVP/SaaS,
סעיף 5.2 F-2.1).

**המערכת היא Multi-tenant**: כל אימייל ייחודי יכול לפתוח חשבון נפרד משלו,
עם הקבוצה/אנשי הקשר/החוקים שלו — מספר ה-Reader היחיד (אותו מספר שהוזן
ב-.env) יכול להיות חבר בכמה קבוצות וואטסאפ בו-זמנית, אחת לכל משתמש.

שיוך קבוצה לחשבון הנכון נעשה **באימות מפורש, לא לפי סדר הרשמה**: בסיום
האשף כל חשבון מקבל **קוד אימות אישי** קצר (6 תווים), המוצג במסך הסיום
ובפאנל הניטור כל עוד הקבוצה לא אומתה. אחרי שמוסיפים את מספר ה-Reader
לקבוצה, יש לשלוח בקבוצה הודעה שמכילה **רק** את הקוד הזה — ורק אז ה-webhook
(`app/main.py` — `whatsapp_reader_webhook`) קושר את הקבוצה לחשבון שהקוד
שייך לו (`app/db.py` — `get_unbound_account_by_verification_code`). כך גם
כשכמה משתמשים נרשמים ומצטרפים לקבוצות שלהם בו-זמנית, אין סיכון ששיוך
כרונולוגי-בלבד יקשר קבוצה לחשבון הלא נכון. הודעת הקוד עצמה היא טכנית
בלבד — היא לא נשמרת כהודעה מנוטרת ולא עוברת דרך מנוע החוקים. בניסיון
הרשמה עם אימייל שכבר קיים המערכת מחזירה שגיאה (409) ומפנה להתחברות.

בסיום האשף המשתמש מחובר אוטומטית (session), ומועבר לפאנל שלו ב-`/dashboard`.
בפעם הבאה הוא מתחבר דרך **http://localhost:8000/login** עם האימייל/סיסמה
שבחר.

## הרצה

שני תהליכים נפרדים, כל אחד בטרמינל משלו:

```bash
./scripts/run_connector.sh    # מפעיל את חיבור הוואטסאפ (Baileys) — לסרוק QR בפעם הראשונה
./scripts/run_core.sh         # מפעיל את שירות הליבה על http://localhost:8000
```

לאחר שהחיבור "מחובר" (ראו סטטוס ב-`/health` או בכותרת הפאנל), פאנל הצפייה
של כל משתמש זמין ב: **http://localhost:8000/dashboard** (לאחר התחברות
ב-`/login`) — מציג רק את הנתונים של אותו משתמש (הודעות/הפרות/התראות/דוחות
של הקבוצה שלו בלבד).

לשליחה ידנית של דו"ח (לבדיקה, בלי לחכות לתזמון החצות) — יש להיות מחוברים
בדפדפן ולהשתמש בכפתור "📧 שלח דוח עכשיו" בתחתית הפאנל (שולח את הדו"ח של
המשתמש המחובר בלבד; `curl` פשוט לא ישא את עוגיית ה-session).

## פאנל אדמין (CRM) — כל המשתמשים והקבוצות במערכת

כניסה ל-**http://localhost:8000/admin/login** עם `ADMIN_PASSWORD` (נוצר
אוטומטית ב-`.env`, ראו הטבלה למעלה) פותחת פאנל ניהול פנימי:

- **http://localhost:8000/admin** — טבלת כל המשתמשים הרשומים: אימייל, שם,
  שם קבוצה, האם הקבוצה כבר "נקשרה" בפועל, רמת הקפדה, וספירת הודעות/הפרות/
  התראות/אנשי קשר לכל אחד. כולל כפתור מחיקה (לניקוי חשבונות בדיקה — בלתי הפיך).
- **http://localhost:8000/admin/accounts/{id}** — אותו פאנל בדיוק שרואה
  המשתמש עצמו (הודעות/הפרות/התראות/אנשי קשר/חוקים מותאמים/דוחות), אבל
  בצפיית-אדמין (לא מחובר בתור המשתמש) + כפתור לשליחת דוח יומי מיידי לאותו חשבון.

הפאנל הזה מיועד לצוות (אתם) בלבד — אין לשתף את `ADMIN_PASSWORD` עם משתמשי הקצה.

## מה כלול בשלב ה-POC (לפי סעיף 3.0 במסמך האפיון, + הרחבת Multi-tenant)

- **Multi-tenant**: כמה משתמשים יכולים להירשם בעצמם (self-service), כל אחד
  עם קבוצת וואטסאפ, אנשי קשר וחוקים נפרדים משלו; מספר קורא אחד (Reader)
  משותף, חבר בכל הקבוצות בו-זמנית. התחברות משתמשים (`/login`) ופאנל אדמין
  (CRM, `/admin`) לצוות לצפייה בכל המשתמשים והקבוצות.
- קליטת טקסט, תמונות וסטיקרים.
- 3 חוקים דטרמיניסטיים + 3 חוקים סמנטיים, מוגדרים ב-`config/rules.yaml` (+
  חוקים מותאמים אישית בשפה חופשית לכל חשבון).
- Shadow Mode אישי לכל חשבון — 48 השעות הראשונות מרגע שהקבוצה שלו נקשרה
  (הפרות נרשמות, לא נשלחות התראות).
- Cooldown (10 דק', לכל חשבון בנפרד) ורשימה לבנה גלובלית לפי `config/rules.yaml`.
- התראות מיידיות במייל (SMTP Gmail) לאנשי הקשר שהוגדרו באשף ההרשמה, בזמן
  אמת עם כל הפרה; ערוץ וואטסאפ Business API זמין להרחבה עתידית.
- דו"ח יומי נפרד לכל חשבון במייל, כולל גרף פעילות שעתי וסיכום נושאים (LLM).
- פאנל HTML (`/dashboard`, לכל משתמש בנפרד) לצפייה בהודעות, הפרות, התראות,
  אנשי קשר, חוקים מותאמים ודוחות + סימון משוב נכון/שגוי על כל הפרה (F-5.5).

## מה **לא** כלול (בכוונה, בהתאם לסעיף 3.0/3.3)

אין חיבור לספק תשלומים, ניהול מנויים/חבילות, PostgreSQL, תורים
(Celery/Redis), תמלול קול/וידאו, פעולות אכיפה אוטומטיות (מחיקה/הסרה/השתקה
— המערכת מתריעה בלבד), הקצאת מספרי Reader נפרדים אוטומטית ממאגר (כל
המשתמשים חולקים מספר קורא אחד ב-POC), או חיבור לפלטפורמות נוספות מלבד
וואטסאפ.

## קריטריון הצלחה (סעיף 3.0)

7 ימים רצופים של פעילות ללא ניתוקים, זיהוי נכון של ≥ 80% מההפרות בבדיקה
ידנית מול הפאנל, ודו"ח יומי שמגיע בזמן.

## הערות פרטיות ומשפט (חשוב לקרוא לפני הרצה על קבוצה אמיתית)

- **גילוי נאות**: ברירת המחדל (`SEND_DISCLOSURE_MESSAGE=true`) גורמת למספר
  הקורא לשלוח הודעה לקבוצה בהצטרפותו, שהיא מנוטרת. אל תכבו זאת ללא ייעוץ
  משפטי — זהו דרישה מטעמי חוק הגנת הפרטיות (סעיף 8 במסמך האפיון).
- **תנאי שימוש**: שימוש ב-Baileys (ספק לא-רשמי) מנוגד לתנאי השימוש של
  וואטסאפ ומהווה סיכון לחסימת המספר. זהו סיכון מחושב שהוחלט עליו במסמך
  האפיון לשלב ה-POC/MVP בלבד (סעיף 10.2, 14).
- **מספרי טלפון**: אינם נשלחים למודל ה-AI (Claude) — רק שמות תצוגה
  (סעיף 10.4). מסד הנתונים ב-POC אינו מצפין אותם (בניגוד לדרישת ה-MVP
  המלאה בסעיף 6) — יש להשלים זאת לפני מעבר לסביבת ייצור עם משתמשים אמיתיים.
- הדו"ח היומי אינו כולל תוכן מלא של הודעות, רק קטעי הפרות (F-7.3).
